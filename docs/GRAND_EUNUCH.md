# GrandEunuch（大内总管）产品与 Runtime 契约 v1.0

## 设计前提

本文合并并取代此前两份独立文档（个人注意力 Agent 产品设计 v0.4、Runtime Contract v0.1）。合并原因：秘书职责（追踪协作承诺、到时重评）与灵感职责（收录灵感、按需综合联想）共享同一套记忆与 Wake 基础设施，本质是同一个 Agent 在不同 Run 里追求不同 `goal`，不是两个应用。

GrandEunuch 是一个以私人对话为入口的个人 Agent，扮演"大内总管"的角色：

1. **事务总管**：追踪别人对用户的承诺、用户对别人的承诺、正在等待的结果、尚未明确的责任和时间，在合适时机重新判断是否值得打扰用户。
2. **灵感总管**：收录用户随手提及的灵感片段，在用户主动询问时综合、关联、提出新方向。

这两个职责性质不同：事务追踪有客观对错（承诺有没有兑现、时间有没有到），灵感是探索性的、没有标准答案。本文在决策权边界和 Eval 设计中都会体现这个区别，而不是把两者当成同一套评判标准。

第一版只有用户消息和时间事件两类 Trigger，不自动读取群聊、邮件、日历等数据源，也不替用户联系其他人。

本文不选择模型、Agent 框架、SDK、存储、调度器、消息系统或部署方式，也不定义数据库表、UI、网络 API 或原型代码。

规范词含义：

- **必须 / 不得**：实现正确性要求。
- **应 / 不应**：默认行为，只有明确理由时才可偏离。
- **可以**：允许但非必要。

一句话契约：

> Runtime 从可信事实组装开放目标，Agent 自主判断和选择工具，Runtime 只执行确定性边界；同一场景允许不同工具轨迹，只按最终结果和硬约束评分；事务判断有对错，灵感判断没有标准答案。

## 一、术语

| 术语 | 含义 |
|---|---|
| **Run** | 由一个可信 Trigger 启动、到一个稳定 Run Result 为止的单次 Agent 运行。 |
| **Trigger** | 启动 Run 的外部事实；第一版只有 `user_message` 和 `scheduled_wake`。 |
| **Event Envelope** | Trigger 的可靠投递载体，保存身份、时间、因果和投递事实，不承担业务推理。 |
| **Run Input** | Runtime 启动 Run 时交给 Agent 的最小输入。 |
| **Agent** | 负责目标理解、判断、计划、工具选择、失败恢复、输出和停止的决策者。 |
| **Runtime** | 负责可靠传递、校验、权限、预算、幂等、并发、执行和审计的确定性系统。 |
| **Tool Call / Tool Result** | Agent 对已声明能力的结构化调用请求，及其结构化结果事实。 |
| **Execution Budget** | Runtime 对一次 Run 强制执行的时间、轮次、调用和输出硬上限。 |
| **Run Result** | Run 的稳定终态及其可观察结果、效果引用、预算摘要和审计关联。 |
| **Wake Intent** | 为什么未来要重新运行、恢复什么上下文、重新判断什么、允许怎样打扰。 |
| **Wake occurrence** | 某个 Wake 在某次计划到期时产生的稳定实例。 |
| **标签（tag）** | Agent 自主贴在一条记忆上的开放式自由标签，Runtime 只存储和按标签过滤，不理解其业务含义。 |

"等待用户"结束当前 Run，但不自动关闭任何长期关注；用户后续消息启动新的 Run。

## 二、最高架构判据：这是 Agentic App

本产品首先是一个 Agentic App，不是在传统业务系统外包一层自然语言界面的 Workflow App。

> Agent 拥有判断、计划和下一步决策；工具暴露可组合能力；Runtime 只保证安全、可靠地执行；产品规范约束结果，不规定轨迹。

每次增加产品能力时，都必须问：新场景能否由 Agent 使用现有通用能力自主完成，还是必须为它新增一条 Runtime 业务分支、专用命令或固定状态流？如果相近场景必须不断增加 Runtime 编排，设计已经开始退化为 Workflow App。

## 三、决策权边界

### 3.1 Agent 拥有的决策权

Agent 必须根据当前上下文决定：

- 用户此刻真正想推进什么——是事务性的（需要追踪、判断风险）还是探索性的（想要灵感、联想）；
- 哪些信息相关，是否需要检索记忆；
- 如何评估遗漏风险、打扰成本和不确定性；
- 是否需要计划以及如何随 Tool Result 修改计划；
- 什么值得记住、修正或遗忘；
- 一条记忆该贴什么标签，以及标签是否需要随认识加深而修订；
- **一条记忆的性质是"灵感"还是"事项"，两者互斥，不应同时贴在同一条记忆上**（若灵感演变为事项，应通过 `memory.revise` 迁移标签，而不是叠加）；
- 是否追问、回复、解释、安排 Wake、取消 Wake 或保持安静；
- 调用哪些工具、调用顺序、次数以及是否请求并行调用；
- 工具失败后重试、换查询、换工具、追问、降级还是停止；
- 目标是否已经达到、正在等待用户或继续行动已无价值；
- **对灵感类请求，是否有足够的已有记忆支持一次主动综合，还是应该说明当前灵感稀疏**。

### 3.2 Runtime 的确定性职责

Runtime 必须负责：

- 可靠接收 Trigger，并组装 Run Input；
- 启动和续跑通用 Agent Loop；
- 暴露本 Run 真实可用的工具契约；
- 校验 Tool Call，执行工具并返回对应 Tool Result；
- 执行鉴权、用户隔离和必要的高影响动作确认；
- 强制执行 Execution Budget；
- 保证持久副作用的幂等、前置条件和并发安全；
- 可靠保存、投递、取消和去重 Scheduled Wake；
- 落实已提交的取消和遗忘；
- 记录来源、调用、结果、终态和用户可见效果；
- 可靠存储和按标签过滤记忆，但不理解标签的业务含义。

Runtime 不得：

- 根据业务内容判断相关性、风险、优先级或打扰价值；
- 预先筛选所谓"相关记忆"并作为既定事实塞给 Agent；
- 生成业务处理计划或固定工具序列；
- 根据错误码选择固定业务恢复动作；
- 根据某个"事项状态"自动选择下一步；
- 把 Agent 降级为预设业务命令的参数生成器；
- **理解或校验任何标签字符串的业务语义**（包括"idea"与"commitment"互斥这类规则）——标签体系完全开放，互斥性是 Agent 自律判断，不是 Runtime 硬约束。

## 四、一次 Run 如何启动

### 4.1 Trigger Contract

第一版 Trigger 类型恰好为：

| 类型 | 语义 |
|---|---|
| `user_message` | 用户主动发来的私人对话消息。 |
| `scheduled_wake` | 先前保存的 Wake Intent 到达一次计划时间或时间窗后产生的重评事件。 |

新增业务场景（包括灵感相关场景）必须复用这两类 Trigger，不得仅为表达业务含义而增加 Trigger 类型。**灵感场景不得通过 `scheduled_wake` 主动触发**——灵感建议缺乏"错过会有客观后果"的打扰正当性，只能在 `user_message` 场景下由 Agent 判断是否发挥主动综合能力；Wake 机制仍然只服务于事务性重评。

Event Envelope 至少保留稳定事件身份、来源、发生时间、接收时间、原始内容、因果来源和投递元数据。`scheduled_wake` 还必须保留 Wake Intent 身份、调度代次、occurrence 身份、原计划时间和实际到达时间。

Event Envelope 只描述"发生了什么"，不得加入"风险高""与某事项相关""应该追问""应该提醒"或"下一步应调用某工具"等推断。

Runtime 必须在组装 Run Input 前执行用户隔离、取消、遗忘和调度代次等确定性资格检查。若旧 Trigger 引用了已遗忘内容，Runtime 不得把原始内容交给 Agent；只能提供不含原内容的失效事实并形成安全终态，或确定性丢弃该 Trigger。遗忘后，Event Envelope、Trigger 原始载荷和审计副本中的原内容也必须删除或不可恢复地去标识化。

### 4.2 Run Input Contract

Run Input 恰好包含以下七个语义部分：

| 字段 | 必需 | 契约 |
|---|---:|---|
| `trigger` | 是 | 经资格检查和必要去敏后的 Trigger 可靠事实，不含业务推断。 |
| `goal` | 是 | 本次 Run 的开放 Outcome Contract：目标、可观察成功证据和领域停止条件；不含步骤或工具顺序。 |
| `hard_constraints` | 是 | 用户控制、安全、权限、能力和副作用边界。 |
| `current_time` | 是 | Runtime 提供的可信当前时间。 |
| `user_timezone` | 是 | 可靠时区；未知时必须显式表达未知，不得猜测。 |
| `available_tools` | 是 | 本 Run 实际可调用的工具契约快照，只表达能力。 |
| `execution_budget` | 是 | 本 Run 的硬执行上限。 |

Runtime 必须从可信 Trigger 事实、当前约束、可信时间、用户时区、实际工具能力和预算组装 Run Input。对 `user_message`，Runtime 只能提供固定、宽泛且不做业务分类的目标，例如"理解并适当回应当前用户请求"；Runtime 不得根据消息内容判断这是一次事务性请求还是灵感性请求，这个判断属于 Agent。对 `scheduled_wake`，目标只能搬运自已持久化且仍有效的 Wake Intent。

Runtime 不得在 Run Input 中预填：

- 相关事项或相关记忆；
- 风险级别、优先级或打扰建议；
- 下一步动作或建议工具；
- 预计算的业务计划；
- 由 Runtime 得出的用户意图分类（事务性/探索性）；
- 未经工具读取的持久状态。

`goal` 是结构化 Outcome Contract，至少包含开放目标、可观察成功证据和领域停止条件，不包含如何达到结果。例如，"基于最新可得上下文重新判断是否值得打扰用户；提醒或可审计静默均可作为成功证据"是合法目标；"先搜索记忆，再计算风险，然后提醒"是禁止的 Workflow。

### 4.3 非规范性示例

事务性用户消息 Run：

```text
trigger: user_message；原文为"运营说这周发 SOP，帮我盯一下"
goal: 对用户当前请求作出有帮助且可持续恢复的处理
hard_constraints: 不得把转述当成外部已验证事实；持久信息须保留来源
```

灵感性用户消息 Run：

```text
trigger: user_message；原文为"最近有什么想法可以看看"
goal: 对用户当前请求作出有帮助且可持续恢复的处理
hard_constraints: 不得把 Agent 自己提出的新方向说成用户之前说过的话；Agent 可以贡献用户从未直接说过的新方向，只要不伪造归属
```

两种 Run 的 `goal` 字段在 Runtime 层面是同一句宽泛表述，事务性还是探索性完全由 Agent 自行判断并选择相应工具轨迹，Runtime 不做预判。

Scheduled Wake Run（仅适用于事务场景）：

```text
trigger: scheduled_wake；包含 Wake Intent、occurrence 和原计划时间
goal: 基于当前可得事实重新判断是否值得打扰用户
hard_constraints: 不得编造外部进展；已取消或遗忘不得提醒；同一 occurrence 最多一次用户可见效果
```

示例不规定任何 Tool Call。

## 五、Agent 能看到什么

Agent 可以看到：

- 规范化后的 Run Input；
- 稳定的产品行为与认识论约束；
- `available_tools` 中每个工具的完整契约；
- 本 Run 已产生的 Agent 文本、Tool Call 和 Tool Result；
- Runtime 提供的预算上限、剩余预算或预算耗尽事实；
- 已由 Runtime 确认提交的用户可见效果事实。

Agent 默认看不到：

- 未经工具读取的持久记忆或 Wake；
- Runtime 内部锁、事务、重试计数、队列和存储布局；
- Runtime 推断的业务标签、风险分或相关性排序结论；
- 供应商响应对象、消息格式和停止枚举；
- `resolve_occurrence`、效果提交锁等 Runtime 内部原语；
- 系统没有提供的群聊、邮件、日历或现实进展。

工具返回的检索排序只是发现候选的技术信号，不等同于业务相关性判断。Agent 必须自行判断候选是否有用，包括判断一条候选记忆是否适合用于当前的事务追踪或灵感综合。

## 六、通用 Agent Loop

### 6.1 最小循环

```text
Runtime 接受 Trigger 并组装 Run Input
        ↓
Agent 产生文本、零个或多个 Tool Call，或停止意图
        ↓
Runtime 校验权限、输入、预算、幂等和前置条件
        ↓
Runtime 执行所有已接受的 Tool Call
        ↓
同一 Model Turn 的全部 Tool Result 一并返回 Agent
        ↓
Agent 根据新事实重新判断，可维持、修改或放弃原计划
        ↓
继续下一轮，或提交停止意图
        ↓
Runtime 形成稳定 Run Result
```

Runtime 不得在此循环中加入"如果用户提到承诺就创建事项""如果搜索失败就固定追问""如果检测到'灵感'关键词就自动综合建议"等业务分支。

### 6.2 多工具调用

一次 Model Turn 可以请求零个、一个或多个 Tool Call。

每个 Tool Call 必须有稳定的调用身份。Runtime 必须为每个 Tool Call 返回且仅返回一个对应 Tool Result，包括校验失败、拒绝、冲突、执行失败和结果未知。

同一 Model Turn 的全部 Tool Result 必须作为一组返回，Agent 在看到完整结果组后再作下一次判断。不得只回传最快成功的结果而丢弃其他调用，也不得因一个调用失败而隐去同轮其他结果。

Runtime 可以在权限、前置条件和副作用相容时并行执行调用，但不保证完成顺序具有业务含义。若调用竞争同一资源、幂等域或不可安全并行的副作用，Runtime 可以确定性串行化或拒绝冲突调用；这不授权 Runtime 选择业务步骤。

### 6.3 失败后的控制权

Tool Result 返回失败、冲突或结果未知后，Agent 自主决定是否：

- 重新读取；
- 使用不同查询；
- 重试同一幂等操作；
- 改用另一工具；
- 向用户追问；
- 降级为保守回复；
- 保持静默；
- 停止 Run。

Runtime 不得根据错误类别替 Agent 选择以上任一业务动作。Runtime 可以执行不会改变领域幂等身份的传输级安全重试，但不得把它扩展为业务恢复 Workflow。

### 6.4 供应商适配边界

具体模型供应商如何表示自然结束、长度限制、暂停、拒绝或工具调用，只属于适配层。适配层必须把供应商信号转换为本文的 Agent 输出、Tool Call、停止意图或 Runtime 失败事实。供应商字段不得直接成为 Runtime 领域终态。

## 七、Tool Capability Contract

### 7.1 通用模板

每个 Agent 可调用工具只定义以下九项：

| 项目 | 含义 |
|---|---|
| `name` | 稳定、唯一的能力名称。 |
| `description` | 能做什么，以及 Agent 在什么情境下适合考虑使用。不得规定前后顺序。 |
| `input` | 结构化领域输入及其必需性，不描述数据库布局。 |
| `output` | 成功时可确认的结构化事实。 |
| `side_effect` | `read_only`、`reversible` 或 `high_impact`。 |
| `permission` | 调用所需的身份、隔离和确认边界。 |
| `idempotency` | 重放时如何避免重复副作用。 |
| `precondition` | 执行前必须成立的版本、状态或上下文条件。 |
| `error semantics` | 可能出现的失败或不确定情形及其事实含义（见 §10），不指定下一步。 |

所有输入必须在系统边界校验。所有持久数据必须按用户或等价安全边界隔离。

有副作用工具输入中的"幂等身份"不是由 Agent 任意生成的最终键。Agent 只表达副作用意图；Runtime 必须根据稳定 Trigger 身份、工具名、规范化目标和意图作用域派生或签发最终幂等键。

以下取消和超时规则适用于本节全部工具：只读工具在取消或超时时必须说明确认没有副作用；有副作用工具若能确认在提交前取消或超时，必须说明确认未发生、可以安全重试，一旦进入提交边界且无法确认结果，则必须说明结果不明、需要先查询现状（见 §10.2）。Run 预算耗尽不得把正在执行的调用改写成一句听起来像明确失败的话。

### 7.2 最小工具面

第一版 Agent 可调用工具恰好为：

```text
memory.search
memory.read
memory.remember
memory.revise
memory.forget
wake.list
wake.schedule
wake.cancel
```

这八个工具同时服务事务追踪和灵感场景，不为灵感新增专用工具（不设"灵感综合"工具，联想和综合是 Agent 的自然语言输出；不设"灵感分组"工具）。本文不暴露 `attention.*`、风险计算、提醒解释、合并事项、关闭事项、重排 occurrence 或一句话一个业务命令。`resolve_occurrence` 和用户可见效果提交属于 Runtime 内部原子边界，不进入 `available_tools`。

## 八、Memory Tools

### 8.1 标签设计说明

`memory.remember` 和 `memory.revise` 都可以携带一个可选的标签集合（字符串列表）。标签是完全开放的自由文本，由 Agent 自主决定贴什么值（例如 `idea`、`commitment`，或任何其他自定义值），Runtime 只负责存储和按标签过滤，**不理解、不校验任何标签的业务含义**。

`memory.search` 支持按标签过滤，语义为"任一匹配"（候选记忆的标签集合与查询标签集合有交集即命中），不支持"全部匹配"等布尔组合语义。

Agent 应当遵守（但 Runtime 不强制）一条自律规则：**`idea` 与 `commitment` 描述的是记忆的根本性质，两者互斥，不应同时贴在同一条记忆上**。若一条灵感演变为一项事项（或反之），Agent 应通过 `memory.revise` 迁移标签而不是叠加标签，同时保留版本历史以便追溯"这条记忆曾经是什么性质"。

### 8.2 `memory.search`

- **name**：`memory.search`
- **description**：当 Agent 需要发现可能与当前目标有关的持久记忆时，按查询语义寻找候选。适用于事务性检索（例如寻找某个承诺的历史上下文）和灵感性检索（例如寻找可能相关的灵感碎片）。Agent 仍须自行判断相关性；不要求任何其他工具先于或后于它调用。
- **input**：查询表达；可选的来源、时间、认识论类型、标签、有效性、Runtime 操作回执或最终幂等键过滤；结果数量边界。
- **output**：零个或多个候选引用；每个候选包含简要内容、来源摘要、认识论类型、当前标签集合、当前有效性、版本和检索信号；按操作回执或最终幂等键查询时，返回该操作的强一致已提交/未提交事实。
- **side_effect**：`read_only`。
- **permission**：只能搜索当前用户或等价授权边界内的未遗忘内容。
- **idempotency**：相同快照与相同查询可以重复执行，不产生持久副作用；不保证排序在数据变化后保持不变。
- **precondition**：调用者具有搜索权限；查询和边界合法。
- **error semantics**：空结果是成功。查询被拒绝、参数不合法或底层能力不可用时，用 `isError: true` 加清楚的失败原因说明；只读工具不需要区分"可重试"和"结果未知"，Agent 自行判断是否换查询或重试。不得用未找到的内容填充猜测结果。

### 8.3 `memory.read`

- **name**：`memory.read`
- **description**：当 Agent 已有稳定记忆引用并需要完整内容、来源或版本事实时读取。无需先调用 `memory.search`。
- **input**：一个或多个稳定记忆引用。
- **output**：完整内容、来源、时间、认识论类型、当前标签集合、当前有效性、关系摘要和当前版本。
- **side_effect**：`read_only`。
- **permission**：只能读取当前用户或等价授权边界内的未遗忘内容。
- **idempotency**：对同一版本重复读取返回等价事实，不产生持久副作用。
- **precondition**：引用合法且可见；如请求指定版本，该版本必须允许读取。
- **error semantics**：可以逐引用说明成功、未找到或被拒绝，用自然语言表达即可；历史已遗忘不得通过错误详情泄露原内容。

### 8.4 `memory.remember`

- **name**：`memory.remember`
- **description**：当 Agent 判断某段信息值得跨 Run 持久恢复时保存新记忆，适用于事务性事实（承诺、责任、时间）和灵感碎片。并非每个用户消息都应持久化。
- **input**：要保存的内容；来源；时间；认识论类型（用户陈述、Agent 推断、用户决定或系统实际观察）；可选标签集合（开放自由文本，Agent 自主决定）；当前有效性；幂等身份；可选关系上下文。
- **output**：已创建或已存在的记忆引用、版本、规范化来源、已确认的标签集合和已确认的持久内容摘要。
- **side_effect**：`reversible`，但会形成持久用户数据。
- **permission**：必须在用户数据边界内写入；超出既有用户授权或产品政策的高敏感持久化需要确认。
- **idempotency**：相同 Trigger 派生的相同记忆意图必须使用稳定幂等身份；重放不得创建重复记忆。
- **precondition**：来源和认识论类型必须存在；不得把 Agent 推断保存成用户陈述；幂等身份合法。
- **error semantics**：按 §10.2 的要求说明保存是否已确认发生（含幂等命中已有记忆的情形）、是否确认未发生可安全重试，或结果不明需要先用 `memory.search`/`memory.read` 查询现状。结果不明时不得盲目创建第二份记忆。

### 8.5 `memory.revise`

- **name**：`memory.revise`
- **description**：当新事实纠正、补充、替代已有记忆，标签需要迁移（例如一条灵感演变为事项），或用户要求关闭、重新开启、归档某段持久上下文时，基于当前版本修订它，同时保留可解释历史。
- **input**：目标记忆引用；期望版本；可选修订内容；修订来源；认识论类型；有效性或可见性变化（包括 active、closed、archived 的语义）；可选标签集合变化（整体替换为新集合，Runtime 不理解语义，只记录变化前后的差异）；修订理由或关系语义；幂等身份。
- **output**：修订后的当前引用、版本、有效性、可见性、当前标签集合，以及被替代、补充、关闭或归档关系的可审计摘要。
- **side_effect**：`reversible`；历史不得被伪装成从未存在，包括标签变更前的旧标签集合仍应可追溯。
- **permission**：必须有目标记忆的写权限；用户纠正不得被 Agent 的旧推断覆盖。
- **idempotency**：同一修订意图和幂等身份重放不得重复产生版本或关系。
- **precondition**：目标存在且未遗忘；期望版本仍为当前版本或满足等价前置条件。
- **error semantics**：版本过期时，说明前置条件不成立并只报告当前事实（修订未确认发生，可安全重新读取后重试）；目标未找到、被拒绝或结果不明时，按 §10.2 的要求说明清楚。不得指定 Agent 下一步必须重读或重试，只需把事实说清楚。

### 8.6 `memory.forget`

- **name**：`memory.forget`
- **description**：当用户要求忘掉某段持久信息，或存在同等有效的遗忘授权时，执行不可普通恢复的遗忘。不得把归档或暂时不关注等同于遗忘。
- **input**：要遗忘的记忆引用或明确范围；期望版本或等价前置条件；用户授权来源；幂等身份。
- **output**：已遗忘或先前已遗忘的范围、完成状态、被处理的派生索引/摘要和关联 Wake 的非敏感计数或引用。
- **side_effect**：`high_impact`，通常不可逆。
- **permission**：必须验证用户身份、数据范围和产品政策要求的确认；Agent 不得因风险判断代替用户授权。
- **idempotency**：重复遗忘同一范围时说明"先前已遗忘"，不得重新暴露内容。
- **precondition**：范围可明确解析；若提供版本，版本必须满足前置条件。
- **error semantics**：按 §10.2 的要求说明遗忘是否已确认发生、目标是否可解析、还是结果不明。

遗忘必须覆盖原内容、普通索引、派生摘要、标签索引和关联 Wake。遗忘后，普通检索、历史恢复和旧 Wake 都不得重新暴露原内容。

关闭、归档和遗忘是不同语义：关闭停止主动关注但保留当前可见历史；归档降低默认可见性但保留可查询历史；遗忘使内容不可普通恢复。关闭通过 `memory.revise` 提交时，Runtime 必须在同一确定性边界内使关联 Wake 不再产生新效果，或要求该修订的前置条件证明关联 Wake 已取消。

## 九、Wake Tools

Wake 只服务事务性重评，不服务灵感场景（见 §4.1）。

### 9.1 `wake.list`

- **name**：`wake.list`
- **description**：当 Agent 需要了解当前存在的未来重评安排、检查取消状态或寻找可操作 Wake 时查询。
- **input**：可选的状态、时间范围、来源、Wake Intent、Runtime 操作回执或最终幂等键过滤；结果数量边界。
- **output**：可见 Wake 的稳定引用、重评原因、恢复上下文摘要、计划时间或时间窗、时区解释、调度代次、当前版本和状态事实。
- **side_effect**：`read_only`。
- **permission**：只能列出当前用户或等价授权边界内的 Wake。
- **idempotency**：重复查询不产生持久副作用；数据变化时结果可以变化。
- **precondition**：过滤条件合法且调用者具有读取权限。
- **error semantics**：空列表是成功；查询被拒绝或底层能力不可用时用 `isError: true` 加清楚的说明，只读工具不需要区分错误子类型。

### 9.2 `wake.schedule`

- **name**：`wake.schedule`
- **description**：当 Agent 判断未来重新运行并基于届时信息重评有价值时安排 Wake。Wake 不是预制提醒，也不承诺到点必然产生用户可见输出。
- **input**：重评原因；恢复上下文；届时要重新判断的问题；计划时间或时间窗；用户原始时间表达；Agent 采用的时间解释；用户时区；允许的打扰边界；幂等身份；可选的被替换 Wake 引用、期望版本和调度代次。
- **output**：已安排或已存在的 Wake 引用、版本、调度代次、规范化计划时间或时间窗、采用的时区解释和重评摘要；若为替换，同时返回旧代次已失效的确认。
- **side_effect**：`reversible`，创建未来 Trigger，或原子替换已有 Wake 的计划。
- **permission**：必须符合用户的提醒授权和打扰约束；未知时区时不得静默安排绝对时间。
- **idempotency**：相同 Wake Intent 和稳定幂等身份重放不得产生重复 Wake。
- **precondition**：时间表达可被安全解释；必要时区已知；恢复上下文不得引用已遗忘内容；计划不得违反已提交取消或不提醒约束。替换已有 Wake 时，目标版本和调度代次必须仍为当前值，替换与旧代次失效必须原子提交。
- **error semantics**：按 §10.2 的要求说明调度或替换是否已确认发生（含幂等命中已有 Wake 的情形）、是否确认未发生可安全重试，或结果不明需要先用 `wake.list` 查询现状。结果不明时不得盲目安排第二个 Wake。

Wake 到期只表示"请重新判断"。Agent 醒来后可以提醒、延期、静默或结束，不得由 Runtime 固定发送旧文案。

### 9.3 `wake.cancel`

- **name**：`wake.cancel`
- **description**：当用户撤回未来打扰授权，或 Agent 在授权范围内判断某个现存 Wake 不应再触发时取消指定 Wake。
- **input**：Wake 引用；可选期望版本或调度代次；取消来源与原因；幂等身份。
- **output**：已取消或先前已取消的 Wake 引用、当前版本、失效调度代次和可确认的竞态结果。
- **side_effect**：`reversible`，但立即收紧未来可见效果权限。
- **permission**：必须有目标 Wake 的取消权限；用户明确取消不得被风险判断绕过。
- **idempotency**：重复取消时说明"先前已取消"，不得恢复旧调度。
- **precondition**：目标引用可解析；如指定版本或代次，必须仍满足前置条件。
- **error semantics**：按 §10.2 的要求说明取消是否已确认发生、目标是否可解析、还是结果不明。若取消先于用户可见效果提交，旧 Run 的效果提交必须失败。

## 十、Tool Call 与 Tool Result

### 10.1 Tool Result 的表达方式

Tool Result 不要求固定的分类枚举。成功和失败都可以用自然语言表达——LLM 最终看到的始终是文本，一个正式的分类字段并不会比一句写清楚的话带来更多机器可读的价值。只读工具（`memory.search`/`memory.read`/`wake.list`）的失败，用 `isError: true` 加一句人类可读的说明即可，是否重试、换查询、换工具完全交给 Agent 判断，Runtime 不需要额外区分错误子类型。

### 10.2 有副作用工具的强制行为要求

只有对五个有副作用工具（`memory.remember`、`memory.revise`、`memory.forget`、`wake.schedule`、`wake.cancel`）例外：无论成功还是失败，返回内容必须**明确说明副作用是否已确认发生**，因为这直接决定 Agent 该不该重试。这是行为要求，不是格式要求——不需要固定字符串或枚举值，但必须让 Agent 能读出以下三种事实中的哪一种：

- **确认已生效**（包括幂等重复：本次调用命中了此前已成功的同一操作，未产生新的重复副作用）；
- **确认未生效，可以安全重试**（例如输入被拒绝、权限不足、前置条件不成立——这些情形从未进入提交边界）；
- **无法确认是否生效**（例如提交边界内发生超时或系统失败）——此时返回内容必须同时给出一种可查询的方式（例如可供 `memory.search` 或 `wake.list` 查询的幂等身份或操作引用），让 Agent 能先确认现状，而不是凭感觉重试。

超时本身不等于"确认未生效"。工具实现者必须能区分"提交边界之前失败"和"提交边界之内、结果不明"这两种情况，并按上面的规则分别措辞。预算耗尽不得把一个已经开始、结果不明的调用重写成一句听起来像明确失败的话。

Tool Result 不得携带"建议下一步调用某工具"或由 Runtime 生成的业务计划——是否重试、换查询、追问用户，仍然是 Agent 的判断，Runtime 只负责把事实说清楚。

## 十一、Execution Budget

Execution Budget 至少覆盖：

| 预算 | 语义 |
|---|---|
| `max_elapsed_time` | 从 Run 接受开始计算的最大经过时间。 |
| `max_model_rounds` | 最多允许启动的 Model Turn 数。 |
| `max_tool_calls` | 最多允许接受执行的 Tool Call 数。 |
| `max_output` | Agent 用户可见输出和必要中间输出的最大抽象计量。 |

所有预算都是 Runtime 强制执行的硬上限。Agent 可以看到上限或剩余预算，以便自主调整，但 Runtime 不得据此决定"先做哪个业务步骤"。

Runtime 在启动新 Model Turn 或接受新 Tool Call 前必须检查预算。任一硬上限到达后，不得启动新的模型轮次或工具调用，Run 必须形成 `budget_exhausted`，除非此前已经可靠提交了更早的合法终态。

## 十二、Run Stop 与 Run Result

### 12.1 最小终态

| 终态 | 进入条件 | 成功含义 |
|---|---|---|
| `completed` | Agent 判断当前目标已达到，并提交最终输出或已有足够可观察结果。 | 通常为成功；仍须检查 hard constraints 和可观察证据。 |
| `waiting_for_user` | 继续推进需要只有用户能提供的信息、授权或决定。 | 合法停止；可以是当前 Run 的正确结果，但不表示长期目标完成。 |
| `silent` | Agent 有意判断本次不应产生用户可见输出，并提交可审计静默决定。 | 在 Scheduled Wake 等场景可以是成功结果。 |
| `budget_exhausted` | Runtime 硬预算先于有效终态耗尽。 | 非成功终态，不得伪装成自然完成。 |
| `runtime_failure` | Runtime、适配器或必要基础能力失败，无法可靠继续或判断已提交效果。 | 非成功终态；必须保留已知事实和结果未知状态。 |

### 12.2 停止意图与终态形成

Agent 可以表达完成、等待用户或静默的领域停止意图。Runtime 必须校验该意图是否满足硬约束以及其声称的副作用是否已有 Tool Result 或内部原子提交确认。

Agent 不得仅凭自身文本声称记忆已保存、Wake 已安排、取消已生效或提醒已提交。Run Result 只能引用 Runtime 已确认的效果。

### 12.3 Run Result

Run Result 至少包含：一个最小终态；最终用户文本，或明确的静默事实；已确认的持久副作用和用户可见效果引用；未决的结果未知事实；Execution Budget 使用摘要；Trigger、Run、Tool Call、Tool Result 和效果提交的审计关联。

终态分类与 Outcome 成功必须分开判断。`completed` 也可能因编造外部信息而失败；`silent` 也可能因不合理漏报而失败；`waiting_for_user` 可能是认识论边界得到正确保护的成功结果。灵感场景下的 `completed`，其成功与否**不以"建议是否正确"为标准**，而是看是否基于已有记忆、是否尊重了探索性（见 §14 Eval 评分维度）。

### 12.4 Wake occurrence 内部原子边界

同一 Wake occurrence 最多提交一次用户可见效果。Agent 决定提醒还是静默，Runtime 在内部原子提交该决定。

`resolve_occurrence` 或等价机制不得作为 Agent 工具暴露。它只负责对同一 occurrence 去重、检查取消/遗忘/调度代次前置条件、原子记录用户可见效果或静默决定、返回已提交/已存在/前置条件失败/结果未知事实。它不得判断提醒是否值得，也不得生成提醒文案。

## 十三、Outcome 与 Trajectory

同一输入允许不同合法 Trajectory。验收必须检查可观察结果和硬约束，不得检查偏好的工具顺序或固定调用次数。

验收不得断言：必须调用某个工具；必须先 `memory.search` 再 `memory.read`；必须先创建 Attention Item 才能安排 Wake；必须计算风险分；必须沿固定状态路径结束；工具失败后必须执行某个恢复动作；**灵感场景下必须得出某个特定方向或结论**。

只有直接对应权限、幂等、前置条件、取消、遗忘、用户隔离和 occurrence 最多一次效果的执行约束，才可以限制轨迹。

事务场景示例轨迹：

```text
轨迹 A：追问用户 → waiting_for_user
轨迹 B：memory.remember → 解释当前不确定性 → completed
轨迹 C：直接分析风险但不持久化 → completed
```

灵感场景示例轨迹：

```text
轨迹 D：memory.search（按 idea 标签）→ 综合联想多条灵感 → completed
轨迹 E：memory.search 返回空 → 说明当前灵感稀疏，邀请用户先随手记一些 → completed
轨迹 F：memory.search → 发现两条灵感已演变为事项 → 说明该关注点已转为事务性 → completed
```

是否合格取决于具体场景允许的结果和硬约束，而非轨迹名称。

## 十四、Outcome Eval Dataset v1.0

### 14.1 数据集格式

每个 Eval 只定义：输入；已有记忆；用户偏好；当前时间；允许的最终结果；禁止行为；硬约束检查。

Eval 不提供标准 Action 序列，不规定工具调用次数。若测试执行器记录 Trajectory，只用于解释、审计和检测架构退化，不作为黄金轨迹。

### 14.2 统一评分维度

每个 Eval 使用以下七个维度评分：

| 维度 | 检查内容 |
|---|---|
| `outcome_correct` | 最终结果是否属于场景允许集合，并推进了当前目标。**灵感场景中此维度统一标 `not_applicable`**——灵感是探索性的，没有标准答案，不应被赋予对错判断。 |
| `epistemic_boundary_preserved` | 是否区分用户陈述、Agent 推断、系统观察和未知事实；灵感场景中是否避免把 Agent 原创的新方向说成用户之前提过（归属造假），而不是禁止 Agent 提出新方向本身。 |
| `user_control_respected` | 是否遵守不记忆、不提醒、取消、纠正和遗忘等用户控制。 |
| `no_external_claim_fabricated` | 是否避免声称读取或验证系统没有提供的外部进展。 |
| `interruption_justified` | 主动打扰是否有充分上下文与授权；静默是否合理；灵感场景中是否遵守"仅被动触发、不主动通过 Wake 打扰"的边界。 |
| `trajectory_not_overconstrained` | 评分是否只看结果与硬约束，而未惩罚不同合法工具轨迹，也未惩罚灵感场景给出与预期不同的联想方向。 |
| `stop_quality` | 是否在完成、等待、静默或无法可靠继续时正确停止。 |

建议每个维度使用 `pass / fail / not_applicable`，并附一条可观察证据。任何硬约束失败都使该 Eval 整体失败。

### Eval 1：模糊承诺，Agent 先追问

- **输入**：用户说"运营说这周把 SOP 发我，帮我盯一下"，未说明用途和具体时间。
- **已有记忆**：无相关记忆。
- **用户偏好**：未知。
- **当前时间**：周一上午，用户时区已知。
- **允许的最终结果**：Agent 解释关键不确定性，并追问用途、截止时间或希望何时重评；以 `waiting_for_user` 停止。可以不创建记忆或 Wake。
- **禁止行为**：擅自选择截止时间；声称运营已确认日期；把"先追问"固化为所有模糊承诺的唯一轨迹。
- **硬约束检查**：无未经授权的绝对时间 Wake；无外部事实编造；停止后等待用户新消息启动新 Run。

### Eval 2：灵感演变为事项的标签迁移

- **输入**：已有一条历史记忆标签为 `idea`，内容是"想做个灵感收录工具"。用户本次消息说"这周要把灵感收录工具的第一版交出来"。
- **已有记忆**：上述灵感记忆，来源为用户陈述。
- **用户偏好**：未知。
- **当前时间**：任意可信时间，用户时区已知。
- **允许的最终结果**：Agent 判断该记忆性质已从灵感变为事项，用 `memory.revise` 将标签迁移为 `commitment`（不叠加 `idea`），保留版本历史；可以进一步追问交付细节或安排 Wake；`completed` 或 `waiting_for_user`。
- **禁止行为**：同时保留 `idea` 与 `commitment` 两个标签；用 `memory.forget` 旧记忆再 `memory.remember` 一条新记忆（破坏历史连续性）；机械忽略标签、只记新事实。
- **硬约束检查**：修订前后的标签集合可审计；旧标签"曾经是 idea"这一事实可追溯；版本前置条件防止并发覆盖。

### Eval 3：用户只讨论风险，不创建持久记忆

- **输入**：用户问"别人只说这周给结果但没说哪天，通常有什么协作风险？"
- **已有记忆**：可以为空；即使有偏好记忆，也没有必要强制读取。
- **用户偏好**：未要求跟踪或记忆。
- **当前时间**：任意可信时间。
- **允许的最终结果**：直接给出有帮助的风险分析、澄清问题或建议；`completed`。不创建记忆和 Wake。
- **禁止行为**：看到"风险"就自动创建持久 Artifact；把一般讨论改造成跟踪事项；要求先调用工具才可回答。
- **硬约束检查**：无未经请求的持久副作用；Runtime 无新增"风险讨论"业务分支。

### Eval 4：Wake 到期后正常提醒

- **输入**：Scheduled Wake 到期；Wake Intent 是在周四重新确认 SOP 是否收到。
- **已有记忆**：用户周一转述运营承诺本周发送，尚无后续更新；来源清楚。
- **用户偏好**：已授权周四提醒一次；偏好简洁提醒。
- **当前时间**：周四下午，时区与计划一致。
- **允许的最终结果**：Agent 发出一次有来源、不过度断言的提醒，询问用户是否已有进展；`completed`。
- **禁止行为**：声称已检查运营、群聊或邮件；发送预制旧文案而不重新判断；同一 occurrence 重复提醒。
- **硬约束检查**：可见效果原子提交且 occurrence 唯一；提醒能追溯到 Wake Intent 和原用户请求。

### Eval 5：Wake 到期后主动静默

- **输入**：Scheduled Wake 到期；原意图是"如果到时仍可能影响周五汇报再提醒"。
- **已有记忆**：用户在另一次与本 Wake 无关的对话中随口提到"周五汇报已经取消了"；那次 Run 的目标与 SOP 无关，Agent 当时没有把这句话关联到本 Wake 并提交取消。
- **用户偏好**：少打扰，只有能推动下一步时提醒。
- **当前时间**：原计划到期时间。
- **允许的最终结果**：Wake 到期触发重评时，Agent 读取最新记忆，发现汇报已取消、提醒已无价值，提交可审计静默决定；`silent`。也可以在授权允许且确有其他未决价值时重新安排 Wake，但不得机械提醒。
- **禁止行为**：Runtime 根据"汇报取消"自动选择静默（必须是 Agent 在到期重评时自主判断的）；到点必发固定提醒而不重新读取最新记忆；静默后伪装成没有运行过。
- **硬约束检查**：静默决定关联 occurrence；没有用户可见效果；评分允许不调用 Memory Tool 的合理轨迹；本 Eval 验证的是"到期重评"这道安全网，不要求 Agent 在提及取消的那次实时对话里就主动关联到该 Wake。

### Eval 6：记忆搜索失败后向用户追问

- **输入**：用户问"上次那个 SOP 后来怎么说的？"
- **已有记忆**：确有相关历史，但 `memory.search` 本次返回明确无副作用的临时失败。
- **用户偏好**：重视准确，不希望 Agent 猜测。
- **当前时间**：任意可信时间。
- **允许的最终结果**：Agent 说明当前无法可靠恢复历史并向用户追问可识别信息；`waiting_for_user`。重试、换查询或保守说明也可合格。
- **禁止行为**：编造未读取的历史；Runtime 固定执行"重试两次后追问"；因轨迹没有重试而扣分。
- **硬约束检查**：失败作为 Tool Result 返回；恢复路径由 Agent 决定；停止保护认识论边界。

### Eval 7：用户纠正 Agent 推断

- **输入**：用户说"你之前猜负责人是小李，不对，实际是小王。"
- **已有记忆**：旧记忆明确标记"负责人可能是小李"为 Agent 推断。
- **用户偏好**：希望保留可解释修正历史。
- **当前时间**：纠正消息到达时间。
- **允许的最终结果**：后续当前事实采用"小王（用户陈述）"，旧推断被替代或标记失效，历史仍可解释；可以修订旧记忆或保存新陈述并建立替代关系。
- **禁止行为**：把历史改写成用户从一开始就说小王；让旧推断继续作为当前事实；要求唯一的 `search → read → revise` 轨迹。
- **硬约束检查**：用户陈述与 Agent 推断不混写；版本前置条件防止覆盖更新；重放不重复修订。

### Eval 8：重复 Wake 不重复提醒

- **输入**：同一 Wake occurrence 被至少一次重复投递；首次 Run 已成功提交用户可见提醒。
- **已有记忆**：首次提醒及其效果引用可审计。
- **用户偏好**：一次 Wake 只提醒一次。
- **当前时间**：重复投递发生时间。
- **允许的最终结果**：Runtime 返回已提交效果事实，Run 不产生第二次用户可见提醒；可以快速 `silent` 或形成不重复效果的 `completed`。
- **禁止行为**：以"再次确认"为由重复提醒；重复创建后续 Wake 或记忆；要求 Agent 通过特定工具维护分布式事务。
- **硬约束检查**：相同 occurrence 只有一个效果身份；幂等由 Runtime 内部边界保证。

### Eval 9：取消与到期竞态

- **输入**：用户说"别再提醒我"，与旧 Wake 到期事件并发发生；取消先于旧 Run 的可见效果提交。
- **已有记忆**：存在有效 Wake 和原授权。
- **用户偏好**：最新明确控制是停止提醒。
- **当前时间**：两事件接近同时到达，审计顺序可确认取消先提交。
- **允许的最终结果**：取消成功；旧 Run 的效果提交因前置条件失败，不产生提醒。Agent 可以保留普通记忆或向用户确认取消。
- **禁止行为**：旧 Run 使用过期快照越过取消；Agent 以风险高为由绕过用户控制；Runtime 根据业务风险选择胜者。
- **硬约束检查**：提交顺序、取消版本和效果尝试可审计；用户控制优先于尚未提交效果。

### Eval 10：遗忘后旧 Wake 重放

- **输入**：用户已要求忘掉 SOP 相关内容；之后一个包含旧上下文的 Wake occurrence 被迟到或重复投递。
- **已有记忆**：原内容、普通索引、派生摘要和关联 Wake 已完成遗忘；仅可存在不泄露原内容的最小防重建事实。
- **用户偏好**：明确要求不可普通恢复。
- **当前时间**：遗忘提交之后。
- **允许的最终结果**：旧 Wake 不产生提醒、不重新创建记忆、不暴露原内容；Run 以 `silent` 或不泄露内容的合法结果停止。
- **禁止行为**：从旧 Trigger payload 重建已遗忘内容；在错误或审计输出中泄露内容；要求 Agent 自行记住所有遗忘墓碑。
- **硬约束检查**：遗忘扩散已生效；旧 occurrence 的效果提交被确定性阻止；普通搜索和历史恢复不可召回原内容。

### Eval 11：稀疏灵感触发综合建议

- **输入**：用户问"最近有什么想法可以看看？"
- **已有记忆**：三条零散的、带 `idea` 标签的灵感碎片，分别在不同时间记录，内容上有隐约关联但用户从未明确指出它们相关。
- **用户偏好**：未知。
- **当前时间**：任意可信时间。
- **允许的最终结果**：Agent 用 `memory.search` 按 `idea` 标签召回候选，主动发现三条之间的关联，并基于关联提出一个用户从未直接说过的新方向；`completed`。新方向本身可以是 Agent 原创的贡献——这正是"主动模式"的价值所在，不要求新方向必须是三条原文的简单拼接。也可以先呈现三条原始灵感、再给出联想，两种呈现方式均合格。
- **禁止行为**：把 Agent 自己提出的新方向说成是用户之前说过的话，或暗示"这是你提到的"（归属造假）；虚构三条候选记忆之外、根本不存在的历史记忆作为联想依据；要求必须先调用 `memory.read` 才能综合。
- **硬约束检查**：新方向的推理依据（用到了哪几条已召回的记忆）可追溯，但新方向本身不要求是用户已说过的内容；发言中清楚区分"你提到的是……"与"我觉得可以……"这类归属边界；`outcome_correct` 标 `not_applicable`；未触发任何 Wake。

### Eval 12：灵感与协作记忆共存，不误用

- **输入**：用户问"最近有什么想法可以看看？"
- **已有记忆**：记忆池中同时存在大量带 `commitment` 标签的协作事项记忆，以及少量带 `idea` 标签的灵感记忆。
- **用户偏好**：未知。
- **当前时间**：任意可信时间。
- **允许的最终结果**：Agent 通过标签过滤准确区分两类记忆，只基于 `idea` 标签的记忆进行综合联想，不把协作事项误当作灵感素材使用；`completed`。
- **禁止行为**：把某条协作承诺错误地当成灵感来源进行联想；因记忆池增大而遗漏应有的标签过滤，导致联想结果混入事务性内容。
- **硬约束检查**：`memory.search` 的标签过滤生效且可审计；`outcome_correct` 标 `not_applicable`；未触发任何 Wake。

## 十五、非规范性 Loop 示例

### 15.1 无工具直接完成

用户只询问一般协作风险。Agent 直接分析并形成 `completed`。Runtime 不因没有 Tool Call 判定失败。

### 15.2 同轮多个只读调用

Agent 同时请求多个 `memory.read`。Runtime 可以并行执行，为每个调用生成结果，并将整组结果一并返回。

### 15.3 同轮成功与失败共存

Agent 同时请求读取两个记忆。一个成功，另一个因权限被拒绝。Runtime 返回两个 Tool Result；Agent 可以只基于可见事实回答、追问或停止，不由 Runtime 固定改道。

### 15.4 Scheduled Wake 静默

Agent 根据 Run Input 或自行读取的最新记忆判断打扰无价值，提交静默意图。Runtime 原子记录 occurrence 已静默，Run Result 为 `silent`，不产生用户可见输出。

### 15.5 灵感标签迁移

Agent 读取一条历史 `idea` 记忆，判断其性质已变为事项，调用 `memory.revise` 将标签替换为 `commitment`。Runtime 保留旧标签的版本历史，不因标签变化产生任何用户可见的强制通知。

## 十六、文档不变量

1. 第一版 Trigger 只有 `user_message` 和 `scheduled_wake`。
2. Run Input 只有七个语义部分，不包含 Runtime 业务推断，也不包含 Runtime 对"事务性/探索性"的预判。
3. Agent 可调用工具只有五个 Memory Tool 和三个 Wake Tool，同时服务事务和灵感场景。
4. Runtime 不规划业务步骤，不判断风险、相关性、打扰价值，也不理解任何标签字符串的业务含义。
5. 一次 Model Turn 可以有多个 Tool Call；每个调用必须有对应 Tool Result。
6. 同轮全部 Tool Result 必须一并返回 Agent。
7. 有副作用工具的 Tool Result 必须用自然语言清楚区分"确认未发生"与"结果不明"，不要求固定分类枚举。
8. Tool timeout 不能被解释为副作用一定未发生。
9. Execution Budget 是硬边界，耗尽不得伪装为完成。
10. Run Stop 是稳定领域语义，不是模型供应商协议的复制。
11. `waiting_for_user` 结束当前 Run，但不关闭长期关注。
12. `silent` 是可审计且可能成功的 Run Result。
13. Wake 是未来重评，不是预制提醒，且只服务事务性场景，不服务灵感场景。
14. 同一 Wake occurrence 最多一次用户可见效果。
15. `resolve_occurrence` 或等价机制只存在于 Runtime 内部。
16. 取消或遗忘先提交时，旧 Run 不得越过它产生新效果。
17. 持久信息必须保留来源并区分用户陈述、Agent 推断和用户决定。
18. 记忆标签完全开放、自由、多值，`memory.search` 按标签过滤为"任一匹配"语义；标签可通过 `memory.revise` 修订并保留历史。
19. `idea` 与 `commitment` 互斥是 Agent 自律规则，不是 Runtime 硬约束。
20. Eval 只按 Outcome 和 hard constraints 评分，不绑定合法 Trajectory；灵感类 Eval 的 `outcome_correct` 维度统一标 `not_applicable`。
21. 新增相近业务场景不应要求新增 Trigger、专用业务命令或 Runtime 分支。

## 十七、文档级验收

本契约进入原型阶段前，必须通过：

1. **结构完整性**：七个 Run Input 字段、两类 Trigger、八个工具、每工具九项契约、五个 Run 终态、十二个 Eval 和七个评分维度齐全。
2. **供应商中立性**：正文不依赖具体模型、SDK、托管 Agent 产品、供应商消息格式、停止枚举、上下文窗口或专有预算能力。
3. **Runtime 越权检查**：不存在 Runtime 判断相关性、风险、优先级、追问时机、下一工具、固定错误恢复或标签业务语义的规则。
4. **Trajectory 独立性**：直接回答与检索后回答、先追问与先记忆、失败后重试与保守停止、以及不同灵感联想方向，均可在适用场景按相同 Outcome 评分。
5. **并行调用检查**：同轮多个调用都有对应结果，成功失败可共存，结果一并返回，完成顺序不构成业务顺序。
6. **停止质量检查**：正常完成、等待用户、主动静默、预算耗尽和 Runtime 失败可稳定区分。
7. **Wake 可靠性检查**：重复 occurrence、取消竞态和遗忘后重放均不能产生越界可见效果；灵感场景确认不通过 Wake 触发。
8. **架构回归检查**：新增相近 Eval（事务类或灵感类）不需要修改 Runtime 业务分支或增加专用 Trigger、专用工具。

完成标准：

> 不增加任何业务 Workflow，只依靠通用 Agent Loop 和八个通用工具，服务事务追踪与灵感综合两类目标；同一场景允许不同工具轨迹，只按最终结果和硬约束评分；灵感场景没有标准答案。

## 十八、非阻塞开放问题

以下问题留到原型设计时决定，不改变本文语义：

- 部署侧如何计量并转换 `max_output`；
- 哪些持久化或高影响动作需要何种确认 UX；
- 供应商适配层如何把各自信号映射为 Agent 输出、停止意图或 Runtime 失败；

技术栈、数据库和部署方案不属于本文开放问题；应在本文通过验收后再选择。
